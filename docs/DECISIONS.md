## 拷问后自定的细节

| # | 决策 | 理由 |
|---|---|---|
| D30 | 订单号显示为 `MMDD-NNN`（取货日期 + 当天第几单，例如 `1024-003`）；数据库里另存完整日期保证唯一 | 你在后台和微信里一眼能看出是哪天的单 |
| D31 | 专属链接用 32 字节加密随机数（base64url，43 个字符），明文存在数据库里，后台可以"复制链接" | 足够长，猜不中；店主需要能把链接重新发给顾客 |
| D32 | 顾客选日期时只显示"可选 / 已满 / 已截止"，不显示"名额较少" | 少一个阈值设置，也不暴露内部产能 |
| D33 | 生产汇总和邮件重试由外部免费定时服务（cron-job.org）按 America/Chicago 时区触发：汇总每天 20:05，重试每 5 分钟 | Vercel 免费版的定时任务一天只能跑一次，而且可能晚最多 59 分钟；外部服务可以按芝加哥时间准点触发，不受夏令时影响 |
| D34 | 邮件采用"先写进数据库的待发队列，再发送"（outbox）。订单写入成功后立即尝试发送；失败的由每 5 分钟的重试补发；同一事件只发一次 | 邮件失败不影响订单，也不会重复发 |
| D35 | 所有金额用"美分"整数存储和计算 | 避免小数误差 |
| D36 | 推荐下一个日期：从顾客选的日期往后，找第一个能完整容纳整个购物车的开放日期；找不到就提示"暂时没有可以容纳这个订单的日期" | 对应 V1.0 第 4 节 |
| D37 | 并发控制：下单和改单时，在事务里先锁住这一天的"开放日期"那一行（`SELECT … FOR UPDATE`），再统计已占用的名额，再写入订单 | 同一天的下单排队执行，不同日期互不影响 |
| D38 | 频率限制：同一 IP 一小时最多 3 笔；同一微信号同一取货日最多 2 笔未确认订单（新订单、已联系）。IP 只存哈希值 | 防手滑和重复提交，同时不保存可以识别顾客的原始 IP |
| D39 | 待确认订单的提醒：每晚的汇总邮件里列出；后台首页顶部也显示"明天还有 N 笔订单没确认" | D9 的配套 |
| D40 | 套餐大小每个商品可设（默认 4）；套餐价可以为空，表示没有套餐 | 新品可能没有套餐 |
| D41 | 布蕾"一批 3 杯"作为商品设置项，只用在生产汇总里显示"要做几批"，不影响名额 | 对应 V1.1 第 4.2 节 |
| D42 | 订单页、后台页设置 `noindex`；订单页不显示任何其他顾客的信息 | 隐私 |
| D43 | 时区一律 America/Chicago；数据库存 UTC 时间戳，取货日期存为不带时区的日期 | 避免夏令时出错 |
| D44 | 店主微信号默认只显示在成功页和订单页；"是否也在首页页脚显示"是设置里的开关，默认关闭 | 首页人人都能看到，由店主决定要不要公开 |
| D45 | 名额按商品的**当前**设置计算，价格按下单时的**快照**计算。改了名额参数后，后台标出因此超限的日期 | 店主改克数或切法，是因为以后真的要这样做 |
| D46 | 店主只能把订单状态往前推（可以跳过中间状态）；点错时用"更正状态"往回改，必须写原因 | 防止误操作，同时留下记录 |
| D47 | 代码仓库改为**公开**（取代 D20 中"私有仓库"一项）。因此邮箱、微信号、密钥、真实顾客数据一律不进仓库，只放在环境变量或数据库里 | [你] 10/21 |
